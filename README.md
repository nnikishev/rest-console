# Relay — SSH-терминал в браузере

Минималистичный интерфейс для подключения к удалённым Linux-серверам. Backend — Django, Channels и Paramiko; frontend — TypeScript, Vite и xterm.js.

## Возможности

- Независимые вкладки терминалов и раскрывающееся меню подключений слева.
- SFTP-панель: просмотр каталогов, загрузка и скачивание файлов до 5 МиБ.
- Интерфейс на весь экран без прокрутки страницы, с прокруткой внутренних областей.
- Интерактивная SSH-оболочка с поддержкой ANSI-цветов, ввода с клавиатуры и изменения размера терминала.
- Подключение по адресу сервера, порту и имени пользователя.
- Аутентификация паролем либо приватным ключом OpenSSH/PEM (Ed25519, RSA, ECDSA).
- Парольная фраза для зашифрованного ключа.
- Подтверждение SHA256-отпечатка SSH-сервера перед аутентификацией.
- Персональные закладки подключений в базе данных: название, host, порт, пользователь и способ входа; опциональное зашифрованное хранение SSH-ключей.
- Кнопка «Этот сервер» для SSH-подключения к машине, где работает backend.
- Обязательный вход в Django-приложение; завершение сессии и отключение SSH.

## Требования

- Linux, Bash.
- Python **3.10+** с модулями `venv` и `pip`.
- Node.js **20.19+** и npm (рекомендуется актуальная LTS-версия).
- Доступ к SSH-порту целевого сервера со стороны машины, на которой работает Django.

Браузер не подключается к SSH напрямую: соединение устанавливает backend.

## Быстрый старт

Из корня проекта выполните:

```bash scripts/install.sh
bash scripts/install.sh
```

Установщик создаёт `.venv`, устанавливает Python- и npm-зависимости, запускает Ruff для всего Python-кода, собирает frontend, применяет миграции и проверяет конфигурацию Django. При наличии `frontend/package-lock.json` используется `npm ci`, иначе — `npm install`.

Создайте пользователя для входа в веб-интерфейс:

```bash manage.py
.venv/bin/python manage.py createsuperuser
```

Запустите приложение:

```bash scripts/start.sh
bash scripts/start.sh
```

Откройте **http://127.0.0.1:8000** и войдите созданной учётной записью. Учётная запись Django и учётная запись удалённого сервера — разные сущности.

Другой адрес и порт:

```bash scripts/start.sh
bash scripts/start.sh 127.0.0.1:8080
```

Скрипт запуска автоматически исправляет и форматирует Python-код, собирает frontend, выполняет миграции и проверки, затем запускает development-сервер Django в foreground. Остановка процесса из другого терминала:

```bash scripts/stop-example.sh
pgrep -af 'manage.py runserver'
kill <PID>
```

## Подключение к серверу

1. Укажите host, SSH-порт (по умолчанию `22`) и имя пользователя.
2. Выберите пароль или файл **приватного**, не публичного, ключа. Максимальный размер ключа — 64 КБ.
3. Для зашифрованного ключа укажите парольную фразу в поле пароля.
4. Нажмите «Подключиться».
5. Сверьте показанный SHA256-отпечаток с администратором сервера по независимому каналу и подтвердите его только после проверки.
6. Работайте в терминале; для завершения используйте `exit` или кнопку «Отключиться».

Подтверждение отпечатка действует для текущего подключения; постоянного хранилища доверенных серверов пока нет. Пароль и содержимое ключа передаются backend; пароли и парольные фразы не сохраняются. Приватный ключ можно явно сохранить в закладке: в БД записывается только зашифрованный текст. Прокси и средства мониторинга также не должны журналировать WebSocket payload.

## Вкладки, меню и SFTP

- Кнопка «☰ Подключения» открывает и скрывает левое меню с закладками и формой входа.
- «+ Вкладка» создаёт отдельный терминал. Каждая вкладка использует собственные SSH-соединение и историю вывода. Выбор закладки при работающей сессии открывает пустую вкладку и заполняет форму.
- Переключение вкладок не закрывает соединения. Крестик завершает соответствующую сессию с подтверждением. Обновление страницы закрывает все соединения; восстановления сессий пока нет.
- Кнопка «SFTP» показывает файловую панель активной вкладки. Панель использует уже аутентифицированное SSH-соединение, без повторной передачи пароля. На сервере должна быть доступна подсистема SFTP.
- Нажатие на каталог открывает его, на файл — открывает текстовый предпросмотр (только чтение, UTF-8, первые 256 КиБ; другие кодировки и бинарные файлы могут отображаться некорректно). HTML и скрипты отображаются текстом и не выполняются. У каждого элемента есть отдельная кнопка «Скачать»: файлы скачиваются как есть, каталоги — ZIP-архивом. Архив включает пустые каталоги, но пропускает символические ссылки и специальные файлы; лимиты — 5 МиБ суммарного содержимого и готового ZIP, 2000 элементов, 32 уровня вложенности и 45 секунд обработки (отдельная сетевая операция может дополнительно ждать до 20 секунд). Можно ввести путь вручную и перейти на уровень выше. Панель хранит свой путь для каждой вкладки независимо от рабочего каталога оболочки.
- Загрузка файла требует подтверждения и создаёт только новый файл, без перезаписи существующих. Лимит одного файла — 5 МиБ, каталога — 2000 записей. Файлы передаются через WebSocket в памяти backend; при обрыве загрузки может остаться частичный файл. Удаление, переименование и возобновление передачи пока не реализованы.
- Файловые операции выполняются с правами SSH-пользователя, без дополнительной песочницы. Не включайте журналирование WebSocket payload. Reverse proxy должен допускать WebSocket-сообщения примерно до 7 МиБ для передачи файла 5 МиБ в base64.
- Страница фиксирована по размеру окна. Прокручиваются только меню, вкладки, история терминала и список файлов. На узком экране меню и SFTP открываются поверх терминала.

## Мониторинг сервера

Кнопка «◴ Мониторинг» открывает правую панель активной SSH-вкладки вместо SFTP/команд. Автообновление — раз в 5 секунд, только пока панель открыта и страница видима; есть ручное обновление. Показатели предыдущего подключения не используются после переподключения.

Показываются CPU (разность счётчиков `/proc/stat` между опросами; первый опрос без процента), число логических ядер, Load Average за 1/5/15 минут, память и swap, uptime, заполнение локальных смонтированных файловых систем (`df -P -k -l`) и дерево дисков/разделов (`lsblk`: размер, тип, ФС, точка монтирования, read-only). Использование CPU трактует iowait как простой; LA не является процентом и сравнивается с числом ядер. Память считается по MemAvailable, при его отсутствии — приблизительно по свободной памяти, buffers и cache.

Сбор выполняется фиксированной read-only командой в отдельном SSH exec-канале, без sudo и без вмешательства в интерактивную оболочку. Нужны Linux `/proc`, `df` и разрешённый SSH exec. Если `lsblk` отсутствует, остальные метрики продолжают отображаться. SMART, физическое здоровье накопителей, RAID-статус и I/O latency не проверяются; «состояние» здесь означает заполнение, структуру и признак read-only. История до 10 минут (не более 180 замеров) хранится только в памяти браузера отдельно для каждой SSH-вкладки и сбрасывается при переподключении/обновлении страницы. Дашборд шире остальных панелей: четыре карточки с графиками CPU, RAM, swap и LA, ниже заполнение файловых систем с цветовой индикацией (75% — предупреждение, 90% — критично) и сворачиваемое дерево устройств. CPU/RAM/swap используют шкалу 0–100%, LA — адаптивную; временные разрывы более 15 секунд не соединяются линией. На узких экранах мониторинг открывается поверх терминала. При ошибке данные остаются последним успешным снимком с сообщением об ошибке, а не текущими показателями.

## Редактор файлов SFTP

Клик по файлу открывает редактор на всю область терминала. Поддерживаются сохранение кнопкой или Ctrl+S (Cmd+S), перенос строк, отступ двумя пробелами по Tab и отображение позиции курсора. Esc и кнопка «Закрыть» предупреждают о несохранённых изменениях; браузер также предупреждает при уходе со страницы.

Редактор CodeMirror показывает номера строк слева, общее количество строк и позицию курсора. Поле «К строке» и Ctrl+G (Cmd+G) позволяют перейти к нужной строке; Ctrl+F открывает поиск. Подсветка автоматически выбирается по имени/расширению для JavaScript/TypeScript, Python, JSON, HTML, CSS, YAML, SQL, TOML, shell, INI/конфигураций, systemd и `.env`/`.env.*`. Для неизвестных расширений используется обычный текст. Доступны Undo/Redo; при открытии другого файла история отмены сбрасывается, чтобы не переносить содержимое между файлами.

Редактируются только полностью загруженные текстовые UTF-8-файлы в пределах `PREVIEW_LIMIT` (сейчас 1 МиБ). Обрезанные файлы, бинарные данные, другие кодировки и смешанные переводы строк доступны только для чтения. Для обычных файлов сохраняется исходный тип перевода строк LF или CRLF. HTML/скрипты не выполняются.

Сохранение требует подтверждения и выполняется с правами SSH-пользователя, без sudo. Перед записью проверяется SHA256 исходного содержимого: если файл изменился, сохранение отклоняется. Проверка и запись не являются атомарной блокировкой: внешнее приложение всё ещё может изменить файл между ними. Запись выполняется в существующий файл, без автоматической резервной копии; обрыв соединения может оставить частично записанный файл. Перед редактированием важных конфигураций сделайте резервную копию.

## Быстрые команды

Кнопка «⚡ Команды» открывает панель с поиском по названию, категории и тексту команды. Категории можно сворачивать. Панели команд и SFTP открываются по очереди, чтобы оставлять место терминалу.

После подключения при открытии панели загружаются три категории: «Статус сервисов» (`sudo systemctl status '<имя>.service' --no-pager -l`), «Последние логи · 150 строк» (`sudo journalctl -u '<имя>.service' -n 150 --no-pager`) и «Следить за логами» (`sudo journalctl -u '<имя>.service' -n 150 -f --no-pager`). Последние логи выводят до 150 записей и завершаются; слежение сначала выводит до 150 записей, затем ожидает новые до Ctrl+C. Параметр `-n 150` ограничивает число записей журнала, а не физических строк: многострочные записи могут занять больше строк. Backend через SFTP читает только верхний уровень `/etc/systemd/system` активного сервера. Включаются обычные файлы и символические ссылки с окончанием `.service`, но не каталоги, `.timer`, `.socket` или содержимое `.wants`. Для безопасности используются имена из букв ASCII, цифр и символов `_@:.−` (обычный ASCII-дефис); необычные имена с shell-метасимволами или обратной косой чертой пропускаются. Кнопка «Сервисы активного сервера» обновляет список. Список относится к конкретной вкладке и не сохраняется в БД.

В разделе «Добавить свою команду» укажите категорию, название и однострочную команду до 4096 символов. Можно выбрать существующую категорию или создать новую. Команды хранятся в БД отдельно для каждого пользователя Django, доступны на всех его подключениях и удаляются кнопкой ×. Не сохраняйте в тексте команд пароли, токены или другие секреты: пользовательские команды хранятся без шифрования.

Нажатие на команду показывает подтверждение с текстом и целевой SSH-сессией, затем отправляет её с Enter в активный терминал. Это не отдельная фоновая команда: убедитесь, что терминал находится в готовой командной оболочке, а не в редакторе, запущенной программе или запросе пароля. Пароль `sudo` вводится непосредственно в терминале и не сохраняется. Просмотр логов продолжается до прерывания; для остановки передайте Ctrl+C через терминал. Перезагрузка страницы по-прежнему закрывает SSH-сессии.

## Закладки и сервер приложения

Заполните параметры подключения, укажите название закладки и нажмите «Сохранить подключение». Закладки хранятся в БД отдельно для каждой учётной записи Django и доступны после повторного входа, в том числе с другого браузера. Нажатие на закладку заполняет форму; пароль или приватный ключ нужно указать заново, если ключ не был сохранён. Кнопка × удаляет закладку вместе с её зашифрованным ключом (копии могут оставаться в резервных копиях БД).

### Сохранение SSH-ключей

Для включения настройте постоянный `SSH_KEY_ENCRYPTION_KEY` в окружении backend. Сгенерировать его один раз:

```bash scripts/key-generation-example.sh
.venv/bin/python -c 'from cryptography.fernet import Fernet; print(Fernet.generate_key().decode())'
```

Сохраните результат в менеджере секретов или защищённой конфигурации окружения сервиса, отдельно от БД. `.env` автоматически не загружается. Не генерируйте новый секрет при каждом запуске: утрата или замена секрета сделает существующие ключи нечитаемыми; автоматической ротации пока нет. Резервируйте секрет отдельно и не добавляйте его в Git.

Выберите способ входа «SSH-ключ», загрузите приватный ключ и отметьте «Сохранить приватный ключ в закладке». При выборе такой закладки файл повторно не нужен; парольная фраза для зашифрованного SSH-ключа вводится при каждом подключении. API возвращает только признак наличия ключа, а backend извлекает ключ по ID закладки с проверкой владельца и использует адрес и пользователя из неё. Для удаления сохранённого ключа удалите закладку; отдельное редактирование пока не реализовано.

Хранилище использует Fernet (аутентифицированное шифрование). Это защищает ключи при отдельной утечке БД, но не при компрометации работающего backend или одновременно БД и секрета шифрования. Используйте HTTPS/WSS, ограниченные SSH-ключи и доступ к серверу приложения.

Кнопка «Этот сервер» заполняет форму адресом `127.0.0.1` и SSH-портом `22` (настраиваются переменными ниже). Это обычное SSH-подключение со стороны backend, а не запуск оболочки процесса Django. На целевой машине должен работать SSH-сервер; нужны его учётные данные. Пользователь Django не является автоматически пользователем Linux.

Если backend работает в контейнере, `127.0.0.1` указывает на контейнер: задайте `LOCAL_SSH_HOST` адресом хоста, доступным из контейнера. Если настроен `SSH_ALLOWED_HOSTS`, добавьте туда также этот адрес. Проверка отпечатка сохраняется для всех подключений.

## Форматирование и проверки

Ruff автоматически запускается при установке и каждом запуске приложения. Отдельный запуск:

```bash scripts/format.sh
bash scripts/format.sh
```

`ruff check --fix` исправляет поддерживаемые нарушения, `ruff format` форматирует весь Python-код. Если остались неисправимые lint-ошибки, скрипт завершается с ошибкой. Ruff не форматирует TypeScript, HTML или CSS.

Проверки без изменения файлов:

```bash scripts/check-example.sh
.venv/bin/ruff check .
.venv/bin/ruff format --check .
.venv/bin/python manage.py check
npm --prefix frontend run build
```

При разработке frontend можно включить пересборку при изменениях (в отдельном терминале):

```bash frontend/package.json
npm --prefix frontend run dev
```

Это `vite build --watch`, а не отдельный dev-сервер. После изменений обновляйте страницу браузера.

## Переменные окружения

Приложение читает переменные из окружения процесса; `.env` автоматически **не загружается**.

| Переменная | По умолчанию | Назначение |
| --- | --- | --- |
| `DJANGO_DEBUG` | `1` | `0` выключает debug-режим и включает secure-cookie |
| `DJANGO_SECRET_KEY` | Только для разработки | В production обязательно задать собственный секрет |
| `DJANGO_ALLOWED_HOSTS` | `localhost,127.0.0.1` | Домены приложения через запятую, без схемы и порта |
| `SSH_KEY_ENCRYPTION_KEY` | Пусто | Постоянный Fernet-секрет для хранения приватных ключей; без него сохранение ключей отключено |
| `LOCAL_SSH_HOST` | `127.0.0.1` | SSH-адрес для кнопки «Этот сервер», доступный со стороны backend |
| `LOCAL_SSH_PORT` | `22` | SSH-порт сервера приложения |
| `LOCAL_SSH_USERNAME` | Пусто | Пользователь SSH для кнопки «Этот сервер»; если не задан, вводится вручную |
| `SSH_ALLOWED_HOSTS` | Пусто | Список разрешённых SSH-host через запятую; пустой список разрешает любые host |

Пример ограничения целевых SSH-серверов при локальном запуске:

```bash scripts/environment-example.sh
export SSH_ALLOWED_HOSTS='10.0.0.12,server.example.com'
bash scripts/start.sh
```

Разрешённые SSH-host проверяются по точному совпадению введённого имени, а не по подсети или разрешённому DNS-адресу. Для строгой изоляции дополнительно ограничивайте исходящие соединения сетевыми правилами.

## Развёртывание и безопасность

**`scripts/start.sh` — только для разработки. Не публикуйте Django runserver в интернете.**

Для production:

- Используйте HTTPS/WSS и reverse proxy с поддержкой WebSocket.
- Запускайте ASGI-приложение `config.asgi:application` через Daphne под supervision.
- Установите `DJANGO_DEBUG=0`, уникальный `DJANGO_SECRET_KEY` и точный `DJANGO_ALLOWED_HOSTS`.
- Настройте HTTPS/proxy-заголовки в соответствии с вашей схемой развёртывания. Не включайте доверие к произвольным proxy-заголовкам.
- Выполните сборку frontend и `collectstatic`, настройте раздачу каталога `staticfiles` через reverse proxy.
- Ограничьте `SSH_ALLOWED_HOSTS` и сетевой доступ backend. Приложение даёт вошедшим пользователям возможность инициировать исходящие SSH-подключения.
- Ограничьте круг пользователей, добавьте rate limiting и лимиты одновременных SSH-сессий на уровне инфраструктуры перед публичным использованием.
- Не сохраняйте приватные ключи в репозитории и не включайте журналирование учётных данных.

Пример команд после настройки production-окружения (раздачу статики и TLS нужно настроить отдельно):

```bash scripts/production-example.sh
npm --prefix frontend run build
.venv/bin/python manage.py migrate
.venv/bin/python manage.py collectstatic --noinput
.venv/bin/daphne -b 127.0.0.1 -p 8000 config.asgi:application
```

Приложение пока не включает запись сессий, постоянный `known_hosts` и автоматические интеграционные тесты с SSH-сервером. Проверки закладок, хранилища ключей, разграничения доступа и операций SFTP с mock-объектами: `.venv/bin/python manage.py test terminal`.

## Структура

- `config/` — настройки Django, HTTP- и WebSocket-маршрутизация.
- `terminal/consumers.py` — SSH-соединение, проверка host key и обмен с терминалом.
- `templates/` — страницы входа и терминала.
- `frontend/src/` — TypeScript и стили.
- `scripts/` — установка, форматирование и запуск.
- `pyproject.toml` — настройки Ruff.
